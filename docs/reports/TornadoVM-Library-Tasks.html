A library task is a node in a TornadoVM TaskGraph that dispatches a native NVIDIA library call instead of a JIT-compiled kernel. It shares TornadoVM-managed device buffers with the surrounding JIT tasks, runs on the same CUDA stream, and is captured into CUDA Graphs alongside them — so a value produced by a @Parallel kernel feeds cuBLAS (and back) with no host round trip and no manual memory management.

This report is derived entirely from the source tree at commit e06a2e5 (branch claude/tornadovm-library-support-doc-mjrg18): the six tornado-<lib> modules, the two JNI modules under tornado-drivers/, the runtime SPI in tornado-runtime, and the interpreter's library-launch path. Where the repository's own documentation and its code disagree, the code wins, and the discrepancy is flagged.

Part I — Mechanism

1. The libraryTask API surface

The entire user-facing addition to TornadoVM is one method on TaskGraph, a sibling of .task(...):

TaskGraph graph = new TaskGraph("hybrid")
    .transferToDevice(DataTransferMode.EVERY_EXECUTION, matrix, vector)
    .task("pre",  MyKernels::preprocess, matrix)                       // JIT
    .libraryTask("sgemv", CuBlas::cublasSgemv,                         // native cuBLAS
            CuBlasOperation.CUBLAS_OP_T.operation(),
            m, n, 1.0f, matrix, lda, vector, 1, 0.0f, output, 1)
    .task("post", MyKernels::postprocess, output)                      // JIT
    .transferToHost(DataTransferMode.EVERY_EXECUTION, output);

try (TornadoExecutionPlan plan = new TornadoExecutionPlan(graph.snapshot())) {
    plan.execute();
}

TaskGraph declares 20 generic overloads of libraryTask, one per arity, each taking a LibraryTaskN<T1..TN> functional interface from TornadoFunctions plus N typed arguments. Arity 20 is the ceiling; the widest factory actually shipped is cublasSgemmStridedBatched at 17 arguments.

The second argument is a factory — a static method reference that returns a LibraryTaskDescriptor rather than performing any work. The descriptor is a four-field record built with a fluent API:

Table 1 — LibraryTaskDescriptor fields (tornado-api)

The Access[] array is the load-bearing part. It is what lets a native call participate in TornadoVM's ordinary dependency analysis without the compiler ever seeing the callee. The cuBLAS factories compute it dynamically — note that beta changes the access class of the output operand:

private static Access[] readOnlyExcept(int numArgs, int outputIndex, float beta) {
    Access[] accesses = new Access[numArgs];
    Arrays.fill(accesses, Access.READ_ONLY);
    accesses[outputIndex] = (beta != 0.0f) ? Access.READ_WRITE : Access.WRITE_ONLY;
    return accesses;
}

With beta != 0, cuBLAS reads C before overwriting it, so the operand is marked READ_WRITE and TornadoVM keeps its device contents live. This is inferred from a value at graph-construction time, which is only possible because the factory runs on the host before the graph is snapshotted.

2. Anatomy of a library task

A library task is a SchedulableTask without a sketch — structurally the same trick as a pre-built task. It never enters the Graal-based JIT pipeline. What it does enter is everything else:

The interpreter's argument-resolution loop is the seam between the two worlds:

for (int i = 0; i < numArgs; i++) {
    final byte argType  = bytecodeResult.get();
    final int  argIndex = bytecodeResult.getInt();
    if (argType == TornadoVMBytecodes.PUSH_CONSTANT_ARGUMENT.value()) {
        callArgs[i] = constants.get(argIndex);
    } else if (argType == TornadoVMBytecodes.PUSH_REFERENCE_ARGUMENT.value()) {
        final DataObjectState globalState = resolveGlobalObjectState(argIndex);
        final XPUDeviceBufferState objectState = globalState.getDeviceBufferState(interpreterDevice);
        callArgs[i] = objects.get(argIndex);
        // Pointer to the first data element on the device, past the array header
        devicePointers[i] = objectState.getXPUBuffer().toBuffer() + TornadoNativeArray.ARRAY_HEADER;
        isReference[i] = true;
    }
}

Everything the provider receives is packaged into a LibraryInvocation: getArg(i) for boxed scalars, getDevicePointer(i) for buffers, isReference(i), getContext(), getTuning(), and isCapturing() — the last of which lets a provider refuse an operation that would be illegal inside a CUDA Graph capture region.

3. The provider SPI

Providers are discovered with java.util.ServiceLoader from LibraryRegistry, lazily and once per JVM (double-checked locking on a volatile List). Adding a library therefore requires no change to tornado-runtime.

Table 3 — TornadoLibraryProvider, the six methods a provider implements
MethodContract
libraryName()Returns the provider id string matched against the descriptor.
canHandle(device)Capability gate. Every shipped provider tests device instanceof TornadoNativeStreamSupport — i.e. CUDA only.
createContext(device, planId)Creates the native handle, binds it to the plan's CUstream, allocates a workspace. Called once per (library, device, execution plan).
prepare(descriptor, context)Idempotent pre-capture hook. Builds and caches per-shape plans/descriptors/workspaces so that dispatch() allocates nothing.
dispatch(fn, invocation)The actual call. Positional marshalling from the invocation to the native entry point.
destroyContext(context)Frees plans, workspaces, and the handle when the execution plan closes.

Two supporting types complete the SPI. LibraryContext is a bare marker interface — each provider subclasses it with whatever state it needs (handle, stream, plan cache, workspace pointer and size). TornadoNativeStreamSupport is implemented by the CUDA backend device and exposes getNativeStream(planId), getNativeContext(planId), and the NVTX range calls.

4. Device pointers, layout, and the alignment consequence

TornadoVM's off-heap arrays (FloatArray, HalfFloatArray, BFloat16Array, DoubleArray, IntArray, ByteArray) store a 24-byte header ahead of the payload. The device pointer handed to a native library is buffer + TornadoNativeArray.ARRAY_HEADER.

Structural consequence. Because 24 is not a multiple of 16, the payload pointer can never be 16-byte aligned even when the buffer base is. TornadoVM therefore guarantees only 8-byte alignment. This propagates directly into the CUTLASS kernels, which are instantiated with kAlign = 4 (four halves = 8 bytes) instead of the 8 (16-byte, 128-bit) that CUTLASS FP16 tensor-core kernels normally use — and which is why the FP16 factories reject shapes where k or n is not a multiple of 4. It is also why cuBLASLt FP8, which requires leading dimensions that are multiples of 16 bytes, is the one path with an explicit alignment caveat in its javadoc.

5. Stream binding and ordering

Each provider binds its native handle to the backend's CUstream during createContext — cublasSetStream_v2, cublasLtMatmul's stream argument, cufftSetStream, cudnnSetStream, cusparseSetStream; CUTLASS takes the stream per call. Everything therefore runs in order on one stream: JIT kernels, H2D/D2H transfers, and native calls, with no host synchronization at the boundary.

The interpreter adds an explicit guard for the non-capture case. When dependency tracking is active it enqueues a marker on the producer events before the native call, ensuring the library sees completed inputs. During capture this is skipped deliberately — a single in-order stream already orders the work, and waiting on pre-capture events would invalidate the capture.

6. prepare() and CUDA Graph capture safety

Device allocation is illegal inside a CUDA Graph capture region. Every library that creates per-shape plans or workspaces — cuDNN, CUTLASS, cuFFT, cuSPARSE, cuBLAS, cuBLASLt — does that work in prepare(), which the interpreter invokes in the pre-compilation pass before capture begins. prepare() is idempotent via a plan-cache lookup, so the per-call dispatch() allocates nothing and is capture-safe.

try (TornadoExecutionPlan plan = new TornadoExecutionPlan(graph.snapshot())) {
    plan.withCUDAGraph();          // iteration 0 captures; the rest replay
    for (int i = 0; i < iterations; i++) {
        plan.execute();
    }
}

One provider goes further and uses the capture flag defensively. cuSPARSE pre-allocates an 8 MiB workspace in prepare(), but the true external-buffer size depends on the sparse structure and is only known at dispatch, from cusparseSpMV_bufferSize. If a matrix needs more than the pre-allocated amount and invocation.isCapturing() is true, the provider raises a clear error rather than corrupting the capture:

long needed = CusparseNativeLib.spmvBufferSize(context.handle, rows, cols, nnz, ...);
context.growWorkspace(needed, invocation.isCapturing());   // throws if growth is needed mid-capture

7. Context lifetime and caching

LibraryRegistry keys contexts on a three-part record:

private record ContextKey(String libraryName, TornadoXPUDevice device, long executionPlanId) {}
private static final Map<ContextKey, LibraryContext> CONTEXTS = new ConcurrentHashMap<>();

Per-plan scoping is what makes cuBLASLt's heuristic cache and cuDNN's convolution plan cache correct: a plan owns its shapes. Two execution plans using the same device get independent handles, workspaces and caches, and closing one frees only its own.

8. Profiling and observability

Library tasks report TASK_KERNEL_TIME alongside BACKEND, DEVICE and METHOD, next to regular tasks, under --enableProfiler console. The timing is host-side, bracketed by stream markers that are waited on, because the CUDA-C backend does not yet expose device-event timestamps for this path:

final boolean profileCall = TornadoOptions.isProfilerEnabled() && !insideCaptureRegion;
if (profileCall) {
    int preEvent = interpreterDevice.enqueueMarker(planId);
    interpreterDevice.resolveEvent(planId, preEvent).waitForEvents(planId);
    profilerStartTime = System.nanoTime();
}

Two consequences follow. Profiling a library task synchronizes the stream twice per call, so it is a measurement mode, not a production one. And it is disabled entirely while capturing, since synchronizing would invalidate the capture.

Independently of the profiler, every dispatch is wrapped in an NVTX range named <library>/<function> (e.g. nvidia/cutlass/cutlassHgemm), so native calls appear as labelled spans on the Nsight Systems timeline next to the backend's own kernel and transfer ranges. This is a no-op without a profiler attached.

nsys profile --trace=cuda,nvtx -o run tornado -m <module>/<MainClass>
nsys stats --report cuda_gpu_trace run.nsys-rep   # library kernels + JIT kernels, same Strm

static int gemmBiasAct(int m, int n, int k, jlong dA, jlong dB, jlong dBias, jlong dD, ...) {
    typename Gemm::Arguments args(

            0, 0, 0, 0, k, n, 0, n);   // ldc = 0 -> row broadcast

}

This is why the six bias-activation factories take no alpha/beta arguments, unlike cutlassSgemm/cutlassHgemm/cutlassBgemm.

Part III — Comparison with the actual NVIDIA libraries

18. Method, and the two questions that get confused

"How does it compare with the actual NVIDIA libraries" splits into two questions with opposite answers, and keeping them apart is the whole point of this section.

QuestionShort answerWhy
Is it as fast? For an operation that is bound, does the TornadoVM path reach the library's own throughput?Essentially yesTornadoVM does not reimplement anything. 29. Where parity holds, and where it breaks

Because TornadoVM invokes the vendor library rather than reimplementing it, the default expectation is parity. The per-call overhead added on the dispatch path is: one ConcurrentHashMap lookup for the context, one linear scan over the (six-element) provider list, N pointer additions, one hash lookup in the provider's dispatch registry, an NVTX push/pop, and an FFM downcall or JNI transition. All of this is host-side and measured in nanoseconds against kernels measured in microseconds to milliseconds. Under CUDA Graph capture even that disappears from the replay path.

Four situations break the parity expectation, in descending order of importance.

1. cuDNN convolution runs a fixed algorithm

The binding hard-codes CUDNN_CONVOLUTION_FWD_ALGO_IMPLICIT_PRECOMP_GEMM and never calls cudnnFindConvolutionForwardAlgorithm or the v7 heuristic query. cuDNN's central value proposition is that it picks among eight algorithms per shape; a caller who fixes one is using cuDNN as a kernel library rather than as cuDNN. Combined with FP32/NCHW — rather than FP16/NHWC, the tensor-core-preferred combination — the measured 11.6 and 21.1 TFLOP/s sit well below what the same GPU reaches on cuBLAS FP32 GEMM (48–57 TFLOP/s, Table 25), let alone its FP16 tensor path. The repository's own README names algorithm autotuning and the FP16 tensor-core path as "the next big steps", so this is a known position rather than an oversight.

2. CUTLASS runs one tile configuration at reduced alignment

A derived comparison, using two different benchmarks on the same GPU at the same size and precision: BenchmarkCutlassGemm reports ≈39 TFLOP/s for FP16 at 1024, while BenchmarkSgemm reports 44.1 TFLOP/s for cuBLAS FP16 at the same size. The CUTLASS path is therefore roughly 0.9× cuBLAS on this shape. Two causes are visible in the source and both are structural rather than incidental:

  • kAlign = 4 — 64-bit operand loads instead of the 128-bit loads a normal FP16 tensor-core CUTLASS kernel uses, forced by the 24-byte array header (§4).
  • A single 128×128×32 tile for every problem, where cuBLAS dispatches among many tuned kernels and the CUTLASS profiler would select per shape.

These are not a controlled A/B — the two benchmarks differ in harness and validation — so treat 0.9× as an indication, not a measurement. The direction is nonetheless what the kernel configuration predicts. CUTLASS's advantage here is not raw GEMM throughput but the fused epilogues and the row-major layout; on a plain GEMM, cuBLAS is the better call.

3. Profiling changes what it measures

Enabling --enableProfiler inserts two stream markers per library task and waits on both. For a short call this can dominate the measurement. NVTX ranges under nsys are the non-perturbing alternative and are always on.

4. Host-pointer scalars under CUDA Graph replay

Not a throughput issue but a correctness trap: α and β are captured by value, so a replayed graph silently reuses the values from capture time. There is no diagnostic; the caller must re-capture or avoid varying scalars.

What TornadoVM adds that the C API does not have. The comparison so far has been one-directional. Against a hand-written C program calling the same libraries, the TornadoVM path adds: automatic buffer lifetime and residency across the JIT↔native boundary; dependency-driven ordering derived from Access[] rather than hand-placed events; CUDA Graph capture of the whole mixed region for free; a uniform profiler and NVTX labelling across JIT and native work; and the ability to write the surrounding pre/post-processing in Java instead of CUDA C. For the operations that are bound, that is a strictly better place to call them from.

32. Writing a provider

The extension story is the strongest part of the design: adding a library touches only the new module. Four steps, mirroring tornado-cudnn:

  1. Factory — a static method returning a LibraryTaskDescriptor with library name, function name, Object[] parameters, and the Access[] array.
  2. Provider — implement TornadoLibraryProvider's six methods; bind the stream in createContext, do all allocation in prepare().
  3. Register — provides ... with MyProvider; in module-info.java and the same class name in META-INF/services/uk.ac.manchester.tornado.runtime.library.spi.TornadoLibraryProvider.
  4. Bind — a SymbolLookup plus downcall handles in java.lang.foreign. A tornado-drivers/<lib>-jni CMake module is needed only when the library requires actual compiled C/C++ (a header-only template library, or an ABI FFM cannot express) — and that path additionally requires wiring in the root pom.xml, the tornado-drivers profile, tornado-assembly (assembly.xml and pom.xml), and tornado.py's --add-modules list.

Four of the six shipped providers took path (4) without a JNI module, which is the evidence that the FFM route is the default and the native module the exception.

Part VI — Assessment

33. Findings

What the design gets right

  1. The Access[] insight. Reusing TornadoVM's existing data-flow machinery by having a factory declare per-argument access — including deriving READ_WRITE from the runtime value of beta — is what lets an opaque native call participate in dependency analysis without the compiler knowing anything about it. Everything else follows from this.
  2. The prepare() / dispatch() split. Hoisting every allocation into a pre-capture hook is what makes native library calls CUDA-Graph-capturable at all, and it is enforced uniformly across six providers with different allocation behaviours.
  3. Zero core-runtime coupling. Six providers exist and tornado-runtime knows about none of them. LibraryRegistry is 60 lines of ServiceLoader and a ConcurrentHashMap.
  4. Self-guarding builds. A missing vendor library degrades to a runtime UNSUPPORTED, never a build failure. This is what makes it viable to ship six optional NVIDIA dependencies in one SDK.
  5. Honest, comparative benchmarks. Every benchmark measures against the best hand-written TornadoVM kernel, not only against sequential Java, and cross-validates results. The SGEMV table — where cuBLAS wins by only 1.4× — is included even though it is the least flattering number in the set.

The limits that matter most

  1. The 24-byte header caps alignment at 8 bytes. This is the one constraint no provider can work around, and it costs measurable CUTLASS FP16 throughput while imposing a user-visible shape restriction. Any future FP8 or 128-bit-load path meets the same wall.
  2. Host pointer mode blocks a whole class of operations. Without CUBLAS_POINTER_MODE_DEVICE, α and β cannot be produced on-device or varied across CUDA Graph replays, and the scalar-output Level-1 routines cannot be bound at all without breaking capture. Roadmap A3/E4 is the highest-leverage unblocking item in the tree.
  3. cuDNN's fixed convolution algorithm. Using one of eight algorithms without heuristic selection forgoes cuDNN's main advantage, and the FP32/NCHW choice forgoes tensor cores on top of that.
  4. cuSPARSE's α=1, β=0. The narrowest provider is narrower than it needs to be — the native layer already takes both scalars as parameters; only the factory signature withholds them.
  5. Inference only, single device. No backward operation anywhere, no multi-GPU, no NCCL. The binding targets inference and numerical kernels, not training.
  6. Not portable. A graph containing a library task runs on CUDA or throws. There is no JIT fallback for the same operation, so portable code must branch at graph-construction time.

Overall

The right way to read this subsystem is as a mechanism with a demonstration set, not as a Java binding for the NVIDIA math libraries. The mechanism — shared device buffers, one stream, dependency-driven ordering, capture-safe preparation, ServiceLoader extensibility — is complete and uniformly applied, and it is the hard part. The 39 entry points on top of it are a curated slice chosen for LLM and CNN inference: GEMM in five precisions, fused MLP epilogues, flash attention, FFTs, CSR SpMV. Where a slice exists it runs at the vendor library's own speed, up to the hardware ceiling. Everywhere else, the honest answer to "does TornadoVM support X" is that adding X is a factory, a registry entry, a downcall handle and a test, in one module, with no core changes — which is precisely what the design was built to make true.
