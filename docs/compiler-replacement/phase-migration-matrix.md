# Phase migration matrix (Phase 2, static part)

Recorded 2026-10-09 on `compiler/main`. Path abbreviations (`RT`, `DC`, `CU`) are the ones defined
in `graal-dependency-map.md`. Purposes are written in our own words from reading TornadoVM-authored
code; no code is reproduced. "Dynamic hits" comes from the Phase 2 trace: the full CUDA `tornado-test` suite with a counting
hook on every top-level tier phase (branch `scratch/phase-trace`, 2026-10-09; raw data
[baseline/phase-trace-aggregate.json](baseline/phase-trace-aggregate.json)). "changed" counts runs
that added or removed graph nodes. Phases that run nested inside another phase (helpers, the
loop unroller inside task specialisation) show 0 here; that is not evidence they are unused. Gate C2 needs every phase or
node that the trace shows executing to have a row with an owner, a replacement and a test.

Columns:
- **Tier**: sketch / high / mid / low / LIR / helper (runs inside another phase) / dead.
- **TC replacement**: proposed TC module, or "not needed: reason".
- **Class.**: MUST (behaviour must exist in TC) / SIMPLIFY (needed, much smaller in TC) / REMOVE (no TC counterpart).
- **Test evidence**: `tornado-unittests` package(s) under `tornado-unittests/src/main/java/uk/ac/manchester/tornado/unittests/` whose kernels use the feature, found by grepping for the API.

Inventory check: runtime `graal/phases/**` has 19 files. 11 are graph phases, plus the empty LIR `TornadoAllocationStage`, 2 inlining policies plus their interface, and 4 tier contexts. `DC/common/compiler/phases/**` has 18 files (17 phases + the `LoopCanonicalizer` helper). `CU/graal/phases/**` contains 21. `CU/graal/compiler` adds `CUDALIRGenerationPhase`, `CUDACanonicalizer`, `CUDAGlobalLoadBatching` and `CUDATileLoopPolicies`, and `CU/graal/lir` adds `CUDAAddressLowering`. OpenCL and Metal hold their own copies of 17 of the 21 CUDA phases. The 4 CUDA-only ones are `CUDADynamicParallelismSupportPhase`, `CUDAKernelContextNullCheckElimination`, `CUDATensorCoreSupportPhase` and `CUDATileSupportPhase`. TC writes each behaviour once; the dialect layer handles the backend differences.

## C. Graal built-in phases TornadoVM relies on (as they appear in the tier lists)

Names only; descriptions are our own.

| Built-in (where) | What TornadoVM uses it for | TC position |
|---|---|---|
| `GraphBuilderPhase` (graph-builder suite; also `RT/analyzer/CodeAnalysis`) | bytecode → sea-of-nodes, with plugins | **needed** → `tc-frontend` (own bytecode → SSA) |
| `CanonicalizerPhase` (sketch, high ×6+, mid ×4, inside TaskSpecialisation and partial unroll) | constant folding, algebraic simplification, branch folding | **needed** → `tc-opt` canonicaliser (Alive2-checked; issue #1149 semantics) |
| `DeadCodeEliminationPhase` (sketch, high ×3, low "Required") | remove dead nodes | **needed** → `tc-opt` DCE |
| `InliningPhase` (+ Tornado policies) (sketch, high) | inline everything reachable | **needed** → `tc-opt` inliner (inline-all + size-cap diagnostic) |
| `IterativeConditionalEliminationPhase` (sketch, high, mid, low) | remove conditions implied by dominating ones | **needed (simplified)**: dominator-based condition propagation in `tc-opt`; mostly helps once guards are gone |
| `PartialEscapePhase` (high) | scalar replacement of short-lived objects (value types, HalfFloat) | **subsumed**: value types are SSA values from the frontend; no general escape analysis |
| `ConvertDeoptimizeToGuardPhase` (high) | turns deopts into guards (later removed by Tornado) | **not needed**: no deopts or guards on GPU |
| `SchedulePhase` (EARLIEST in high, LATEST_OUT_OF_LOOPS in low) | places floating nodes into blocks (and gives the LIR its order) | **subsumed**: TC IR is block-structured; code motion is done by explicit LICM/sinking passes |
| `LoopFullUnrollPhase` (high, tile-aware policies) | full unroll of small counted loops | **needed** → `tc-opt` full unroll (merged with TornadoLoopUnroller behaviour) |
| `HighTierLoweringPhase` / `MidTierLoweringPhase` / `LowTierLoweringPhase` (+ `DefaultJavaLoweringProvider` via `CUDALoweringProvider`) | expand Java semantics (indexed/field access, div/rem, new arrays, thread ids, snippets for reductions) | **needed (simplified)** → `tc-tornado` lowering table; no snippet engine |
| `RemoveValueProxyPhase` (mid) | drop loop-exit proxies | **not needed**: block arguments carry loop-exit values |
| `GuardLoweringPhase` (mid), `UseTrappingNullChecksPhase` (low) | lower remaining guards to control flow / implicit checks | **not needed**: no guards |
| `FrameStateAssignmentPhase` (mid) | attach deopt frame states | **not needed**: no deopt on device |
| `ReassociationPhase` (mid) | reassociate integer expressions for constant folding / invariance | **needed (later)**: optional `tc-opt` pass, only for integer address arithmetic (never fp) |
| `FloatingReadPhase` (via Tornado's modified copy, mid) | memory-dependence-aware load floating | **subsumed** by `tc-opt` load forwarding / LICM over explicit memory effects |
| `FixReadsPhase` (low, `tornado.enable.fix.reads`) | pin floating reads back, fold stamps | **not needed**: no floating reads |
