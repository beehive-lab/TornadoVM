The slow kernel: paged flash attention

Before the fix, processHeadsFlashAttentionFP16Paged (Llama) was the only kernel where TC lost, and it was 1.40× slower. It runs once per layer per token and its work grows with the context, which is why pp512 lost 8% overall while pp128 still won. Nsight Compute on a late launch (context ≈ 500, --launch-skip 7900):

The FFMA counts are within 2%: NVRTC already contracts TC's a*b + c into FFMA, so a TC-side FMA peephole would not have helped here. TC also had no local-memory traffic.

The extra 27% of instructions are almost all one opcode. In the SASS that actually ran (from the Nsight Compute source page), 24.7% of TC's warp instructions were R2UR, moves from regular to uniform registers. In this kernel every lane of a block computes the same 64-float output[] (the scores and V tile live in shared memory and the loop bounds are uniform), so ptxas placed the accumulators in uniform registers. FFMA cannot write a uniform register, so every accumulation was followed by a move back:

FFMA R16, R35, R16, UR57
FADD R33, R35, R33
FFMA R4,  R35, R8,  R4
...
R2UR UR57, R16

TC before the fix: 44 registers, accumulators in uniform registers

LDS.128 R88, [R116+0x80]
FFMA R64, R117, R96, R64
FFMA R65, R117, R97, R65
FFMA R66, R117, R98, R66
FFMA R67, R117, R99, R67

Graal: 164 registers, accumulators in ordinary registers, LDS.128 with immediate offsets

Reproduced offline by compiling both emitted sources through NVRTC 12.6 with TornadoVM's options (perf/jitllm/nvrtc.py), then unrolling one loop at a time with #pragma unroll. The deciding loop was not the one over the private array: it was the 64-trip dot product score += q_shared[d] * k_tile[t*64 + d]. Kept rolled, it leads ptxas into the uniform-register allocation; unrolled, the kernel compiles to 156 registers with no R2UR and no stack. Graal fully unrolls every constant-trip loop that fits a size budget; TC's FullLoopUnroll stopped at 8 trips.

Fix (commit 19f2f3dce): FullLoopUnroll now unrolls up to 64 trips and 1024 instructions after unrolling, or 4096 instructions when the loop touches a private array. The attention kernel now takes 0.81× Graal's time (62.8 µs vs 77.2 µs in prefill), with 156 registers and no stack, against Graal's 164 registers and 256-byte stack.

What this means for the next steps

  1. Generated code shape matters more than any single peephole. TC's CUDA is clean, but how readable source maps to SASS depends on ptxas heuristics (uniform datapath, unrolling, register budget). Keep a standing nsys + ncu + offline-NVRTC loop (scripts in docs/compiler-replacement/perf/jitllm) and treat per-kernel R2UR counts, registers and stack frames as regression signals, not only end-to-end tokens/s.
  2. FMA contraction (O11) is not a CUDA priority. NVRTC already contracts (equal FFMA counts). It matters for OpenCL, where contraction needs -cl-mad-enable or an explicit fma, and for Metal: implement it with the OpenCL dialect.
  3. Largest remaining kernels are at parity, not ahead. fullyFusedRmsNormFFNGateUpQ8 (25% of Llama prefill time), matrixVectorGenericQ8Byte and the Qwen matrixVectorGenericSimd32 family take the same time under both compilers. They are bandwidth-bound matvecs, so the next gains come from memory-level parallelism (Q4 global-load batching) and from checking with ncu whether they reach DRAM bandwidth.
  4. Small losses to close: ropeRotationWithCacheCopyPrecomputedFP16Paged 1.05×, juliaset 1.09×, addImage/copy within 3%. Each needs an ncu look like the attention kernel's.
  5. Benchmark-only gaps: the tornado-benchmarks blurFilter (TC-E1003) and renderTrack (TC-E1002) kernels still fall back to Graal. They are outside the unit-test suite, so run 5 did not see them. Add tornado-benchmarks to the parity harness.
  6. Cold compile latency (1.4–2× Graal's front end in a fresh JVM) is the remaining C7 item. Options: a TC warm-up at runtime start, a CDS/AOT cache for TC's classes (Leyden, Phase 9), and profiling the frontend and structurizer with JFR, whose events are already in place.
  7. Batched prefill (--with-prefill-decode, the MMA path) is not in this bench. Measure it next: it exercises the tensor-core kernels TC compiles differently from the SIMT path.
